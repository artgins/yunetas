Yuneta 7.26.0: history reads 16% faster, a tm query of any topic 31x faster

7.26.0 changes how timeranger2 reads and how its followers hear deletes. The md2 rows of a scan are read 1024 at a time with one pread(), and the match condition is parsed once per scan instead of once per row; the tm markers of 7.25.5..7.25.22 are gone, so a tm condition is a filter on every row of any topic; a key delete reaches the rt_disk followers with the master's delete sequence; and a link in a treedb publishes the relationship, not the parent collapsed whole. Measured against 7.25.22 on the same machine, each release built from its own tree, the two run alternately: reading a history is 16-17% faster, opening a treedb 20% faster, a replica opens 12.6% faster, and a tm query of a topic 7.25.22 had not marked takes 12.8 ms instead of 402. One price, said with its reason: a tm query of a topic 7.25.22 HAD marked takes 12.8 ms instead of 7.5 (it now reads every row). A second one, found by this A/B -- the first open of a topic as master wrote its delete record durably, doubling the time to create 10 topics -- was fixed before the tag: the record is written not durably (it holds 0), and both figures are back within the noise.

The tm markers are gone (API removal): a tm condition filters every row of the key, and no file is left out by its tm range. 7.25.22 skipped the files a marked topic said were out of range; 7.26.0 reads all 600 000 rows, in blocks of 1024 and with the condition parsed once per scan, which is what keeps the cost at 1.7x the marked topic and not 53x (the unmarked topic of 7.25.22, below). 1 key, 30 files x 20 000 rows.

How it was measured

7.26.0 against 7.25.22. 7.25.22 and 7.26.0 each built from their own tree: a git worktree of the 7.25.22 tag with the same .config and compiler, where only the kernel libraries, the modules of modules/c, the benchmarks of performance/c/ and the three ctest binaries were built. outputs_ext was shared between the two trees: linux-ext-libs did not change in this release. Measured: the benchmarks of performance/c/ and the ctest binaries test_topic_pkey_integer, test_topic_pkey_integer_iterator2 and test_topic_pkey_integer_iterator5. The two binaries of each benchmark run alternately, the order flipped every round, with a sync and a 3 s pause before each run: 8 rounds, 24 for the three ctest binaries. Mean +- standard deviation (median). The treedb figures are CPU time of the process per operation. No module was padded or relinked: a whole-release build also moves where the code lands, so a change of a few percent is not told apart from placement. Not measured: a key delete on a topic with an rt_disk feed (no benchmark deletes keys under a feed); by construction it costs two fsyncs and a rename more than in 7.25.22 (the record of the delete sequence). Two figures, tr2.create_topic and ctreedb.seed, were measured again on the 7.26.0 side after the record of the delete sequence was made not durable at its creation (8 rounds, sync and 3 s pause, not alternated).

Absolute figures. The absolute figures of 7.26.0 are its side of the A/B run (the code of the tag, built from the main tree at the version bump): 8 rounds of the benchmarks of performance/c/, 24 of the three ctest binaries, a sync and a 3 s pause before each run, no CPU pinning. The per-second benchmarks drop their first and last second; reads page by page are the FORWARD pass.

Machine. 11th Gen Intel Core i7-11370H @ 3.30 GHz, 4 cores / 8 threads (up to 4.8 GHz), 31 GiB RAM, Samsung SSD 990 PRO 2TB (NVMe) (ext4), Linux 7.0.0-38-generic x86_64, Ubuntu 26.04.1 LTS, glibc 2.43, gcc 15.2.0. Acer Nitro AN517-53. A development machine, with other work running at times; the A/B runs are alternated for that reason.

Build. RelWithDebInfo (-O2 -g -DNDEBUG), gcc 15.2.0, fully static: yes, TLS: OpenSSL 3.6.3 (bundled, static); mbedTLS not built on this machine. CONFIG_DEBUG_TRACK_MEMORY is on (the .config of this machine): every allocation is tracked. A build without it does less work per allocation; that build was not measured here.

The benchmarks are in performance/c/; the raw figures of this page are in 7.26.0.json; every A/B, change by change, is in performance/c/README.md and in the CHANGELOG.
