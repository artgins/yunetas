Yuneta 7.27.7: three reviews of retention, at the speed of 7.27.5

7.27.7 closes three reviews of the retention that 7.27.5 gave timeranger2: the bounds of an iterator on a replica whose numbering a purge moved, the order of a purge and the links of its feeds, a base read again after a failure that passes, the reads an rt_disk follower owes after running out of descriptors, the parts of a multi-key C_TRANGER iterator. None of it costs a read. Against 7.27.5, the last release with a study, on the same machine, 40 of the 41 figures stay inside their noise: the read path of the master and of a replica, the appends, the opens of a store, the treedb writes, the event loop, TCP and TLS. The one outside comes from 7.27.6, which shipped without a report: a forced treedb delete takes 21% more CPU (43.6 -> 52.8 us), because every deleted key is now moved out of keys/ whole before it is removed, so a delete that fails half way never renumbers a key.

Prices paid on purpose

What got slower, how much, in which release, and what it buys.

Forced delete of a treedb node (since 7.27.6)

+21.1%

Since 7.27.6 (commit 503c23efb, the only C change of that release) every key a delete removes is first moved out of keys/ whole, by a rename(), and then removed. A removal that failed half way left part of the key's files; the key, read again from them, moved the rows after the hole, and its next appends took g_rowids that followers and clients had seen. 7.27.5 moved only a key with a base. Placed by the rotation: 7.27.5 43.6 us, 7.27.6 52.7 us, 7.27.7 52.8 us (+0.3% against 7.27.6, t = 0.8). An attribution build of 7.27.7 that reads the start time of the process once takes 47.7 us: about 5 us of the 9.2 us is process_start_time(), a read of /proc/self/stat made at every delete to name the moved directory, and about 4 us the rename. CPU time per delete.

How it was measured

7.27.7 against 7.27.5. Written on 2026-10-22, before the tag. 7.27.7 is the C code of the release: the main tree at 63d12373d (YUNETA_VERSION still says 7.27.6; the bump to 7.27.7 changes no C code). It is measured against 7.27.5, the last release with a study; 7.27.6, which changed .c files and shipped none, runs in the same rotation, so a move is placed in the release where it appears. The three each built from a git worktree, with the same .config and compiler; outputs_ext shared (linux-ext-libs 1.24 at all three). In each tree only the kernel libraries, the modules, performance/c/ and the three ctest binaries were built; the perf_timeranger2 of the main tree (with its read phase, public API only) was compiled into all three. The three binaries of each benchmark run in rotation, the order turned every round and reversed every third, with a sync and a 3 s pause before each run (1 s for the three ctest binaries and the read phase): 8 rounds; 24 for perf_tr_treedb, the TCP and TLS echo and the event loop echo with an append (out of their noise, or at its edge, after 8); 48 for the read phase alone; perf_rotatory 16, its round 8 of 8 left out: something on the machine slowed the three builds alike for that minute (a log line 574 ns against 368 ns, on all three). An attribution build (7.27.7 with process_start_time() read once per process in remove_key_directory(), never shipped) ran perf_tr_treedb in the same rotation, 16 rounds. Mean +- standard deviation (median), t = the change over its standard error; |t| < 3 is noise. The treedb figures are CPU time of the process per operation.

Absolute figures. The absolute figures of 7.27.7 are its side of the A/B run: its C code (the main tree at 63d12373d, before the version bump), built on 2026-10-22 on the machine of the earlier reports. The per-second benchmarks drop their first and last second; reads page by page are the FORWARD pass. The binary sizes are those of the release build of the main tree at the same commit.
