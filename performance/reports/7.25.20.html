Yuneta 7.25.20: the treedb a quarter faster, and nothing slower

7.25.20 closes the fifteen releases since the last report (7.25.5): fixes to the agent, the file watcher, the TCP writes, the SWITCHS macro and the masking of secrets. None of them was meant to change speed, and one of them is the largest gain of the round: SWITCHS stopped compiling a regular expression every time a switch was entered, so treedb writes run 16-25% faster and 40 treedbs start twice as fast. Measured against 7.25.5 on the same machine, each release built from its own tree, the two run alternately. No figure got slower beyond the spread of its rounds.

How it was measured

7.25.20 against 7.25.5. 7.25.5 and 7.25.20 each built whole from their own tree (a git worktree of the tag for 7.25.5; the same .config, compiler and external libraries): the benchmarks of performance/c/ and the ctest binaries test_topic_pkey_integer, test_topic_pkey_integer_iterator2 and test_topic_pkey_integer_iterator5. The two binaries of each benchmark run alternately, the order flipped every round, with a sync and a 3 s pause before each run: 8 rounds, 24 for the three ctest binaries. Mean +- standard deviation (median). Unlike the 7.25.5 report, no module was padded or relinked: a whole-release build also moves where the code lands, so a change under ~2.5% on an append is not told apart from placement.

Absolute figures. The absolute figures are the 7.25.20 side of the same run, on the build of 7.25.20: 8 rounds (24 for the ctest binaries), no CPU pinning. The per-second benchmarks drop their first and last second; reads page by page are the FORWARD pass.

Machine. 11th Gen Intel Core i7-11370H @ 3.30 GHz, 4 cores / 8 threads (up to 4.8 GHz), 31 GiB RAM, Samsung SSD 990 PRO 2TB (NVMe) (ext4), Linux 7.0.0-34-generic x86_64, Ubuntu 26.04.1 LTS, glibc 2.43, gcc 15.2.0. Acer Nitro AN517-53. A development machine, with other work running at times; the A/B runs are alternated for that reason.

Build. RelWithDebInfo (-O2 -g -DNDEBUG), gcc 15.2.0, fully static: yes, TLS: OpenSSL 3.6.3 (bundled, static); mbedTLS not built on this machine. CONFIG_DEBUG_TRACK_MEMORY is on (the .config of this machine): every allocation is tracked. A build without it does less work per allocation; that build was not measured here.

The benchmarks are in performance/c/; the raw figures of this page are in 7.25.20.json; every A/B, change by change, is in performance/c/README.md and in the CHANGELOG.
