Yuneta 7.25.22: two reviews closed, and a forced delete 39% faster

7.25.22 closes two reviews -- of 7.25.21, and of the fixes made for it -- and the open defects of the list it inherited: the agents run as native systemd units, a connection can be dropped from any callback of TLS or TCP without a use of freed memory, a yuno alive but not connected can be killed, the rt_disk followers of timeranger2 hear what they used to lose (a key directory they could not watch, an end of their events they could not count), C_AUTHZ and the IdP stop handing roles and keys to whoever asks, and a stats reset resets. Measured against 7.25.21 on the same machine, each release built from its own tree, the two run alternately: a forced delete in a treedb takes 39% less time, because a delete no longer walks every open key. Four other figures moved beyond their spread on code that did not change -- two a little slower, two faster -- and are said, not claimed: that is where the code landed.

Prices paid on purpose

What got slower, how much, and what it buys.

None. No change of 7.25.22 makes a measured path slower. Two figures moved beyond their spread in that direction: 600 000 appends (-1.9% appends per second, -1.6% with a live reader) and a treedb update in memory (+5.0% of time). Neither path changed in this release -- the append code, tr_treedb.c, kwid.c and jansson are the same -- and on the same code the appends to a store of many keys moved the other way (-8.5% of time), as the update in memory did in the report of 7.25.21 (-5.2%). Both releases are built whole, so the code lands at other addresses: that is placement, not speed, and it is said with its figure.

How it was measured

7.25.22 against 7.25.21. 7.25.21 and 7.25.22 each built from their own tree: a git worktree of the 7.25.21 tag with the same .config and compiler, where only the kernel libraries, modules/c/test, the benchmarks of performance/c/ and the three ctest binaries were built. outputs_ext was shared between the two trees: linux-ext-libs did not change in this release. Measured: the benchmarks of performance/c/ and the ctest binaries test_topic_pkey_integer, test_topic_pkey_integer_iterator2 and test_topic_pkey_integer_iterator5. The two binaries of each benchmark run alternately, the order flipped every round, with a sync and a 3 s pause before each run: 8 rounds, 24 for the three ctest binaries. Mean +- standard deviation (median). No module was padded or relinked: a whole-release build also moves where the code lands, so a change of a few percent is not told apart from placement.

Absolute figures. The absolute figures of 7.25.22 are its side of the A/B run (the code of the tag, built from the main tree before the version bump): 8 rounds of the benchmarks of performance/c/, 24 of the three ctest binaries, a sync and a 3 s pause before each run, no CPU pinning. The per-second benchmarks drop their first and last second; reads page by page are the FORWARD pass.

Machine. 11th Gen Intel Core i7-11370H @ 3.30 GHz, 4 cores / 8 threads (up to 4.8 GHz), 31 GiB RAM, Samsung SSD 990 PRO 2TB (NVMe) (ext4), Linux 7.0.0-38-generic x86_64, Ubuntu 26.04.1 LTS, glibc 2.43, gcc 15.2.0. Acer Nitro AN517-53. A development machine, with other work running at times; the A/B runs are alternated for that reason.

Build. RelWithDebInfo (-O2 -g -DNDEBUG), gcc 15.2.0, fully static: yes, TLS: OpenSSL 3.6.3 (bundled, static); mbedTLS not built on this machine. CONFIG_DEBUG_TRACK_MEMORY is on (the .config of this machine): every allocation is tracked. A build without it does less work per allocation; that build was not measured here.

The benchmarks are in performance/c/; the raw figures of this page are in 7.25.22.json; every A/B, change by change, is in performance/c/README.md and in the CHANGELOG.
