Yuneta 7.27.0: a hardening release that holds its speed

7.27.0 is a hardening release, out of nineteen more rounds of review: the command parser types every parameter, secrets are masked in more places of the logs, the walks of the gobj tree survive a callback that destroys a child, and a NUL in an id, a pkey2 value, an fkey reference or a string of a record is refused. Measured against 7.26.9 on the same machine, each release built from its own tree, the two run alternately: 30 of the 31 figures stay inside the noise of their rounds -- the appends, the reads, the opens of a store, the event loop, TCP and TLS through the gobj stack, the logins of the BFF and the agent audit. One price, said with its number and its cause: a treedb update in memory takes 6.5% more CPU (2.31 to 2.46 us), the two NUL checks every treedb write now makes; with them taken out of the same code, the update is back to 7.26.9.

Prices paid on purpose

What got slower, how much, and what it buys.

A treedb update in memory

The NUL checks of every treedb write (refuse_node_name_with_nul(): the id and each pkey2 value; refuse_fkey_ref_with_nul(): a walk of the kw for a NUL before any fkey reference is read): a NUL used to cut a name where C read it, so a node was indexed under one name and saved with another. Attributed by relinking: the 7.26.9 timeranger2 library with the 7.27.0 gobj-c is not slower (-4.8%), and the 7.27.0 tr_treedb.c with only those two checks taken out runs at 2.328 us against 2.327 us of 7.26.9 (16 alternated rounds; the same code with the checks, +3.8%, t = 3.2). About 0.1 us per write, kept by decision.

How it was measured

7.27.0 against 7.26.9. 7.26.9 and 7.27.0 each built from their own tree: a git worktree of the 7.26.9 tag with the same .config and compiler, where only the kernel libraries, the modules of modules/c, the benchmarks of performance/c/ and the three ctest binaries were built. outputs_ext was shared between the two trees: linux-ext-libs did not change in this release (1.23 at both tags). Measured: the benchmarks of performance/c/ and the ctest binaries test_topic_pkey_integer, test_topic_pkey_integer_iterator2 and test_topic_pkey_integer_iterator5. The two binaries of each benchmark run alternately, the order flipped every round, with a sync and a 3 s pause before each run: 16 rounds (8, then 8 more, because other work on the machine during rounds 2 to 4 had widened the spreads); the three ctest binaries 24 rounds, 1 s pause. Mean +- standard deviation (median), t = the change over its standard error; |t| < 3 is noise, as in the reports before. The treedb figures are CPU time of the process per operation. No module was padded or relinked: a whole-release build also moves where the code lands, so a change of a few percent is not told apart from placement. The one figure outside its noise was then attributed by relinking perf_tr_treedb (perf profiling is not permitted on this machine): with the 7.26.9 libtimeranger2.a and the 7.27.0 gobj-c, and with the 7.27.0 tr_treedb.c compiled with and without its two NUL checks, 16 alternated rounds each.

Absolute figures. The absolute figures of 7.27.0 are its side of the A/B run (the code of the release, built from the main tree after a clean build, with YUNETA_VERSION not yet bumped): 16 rounds of the benchmarks of performance/c/, 24 of the three ctest binaries, a sync and a pause before each run, no CPU pinning. The per-second benchmarks drop their first and last second; reads page by page are the FORWARD pass. The binary sizes are those of the clean release build.

Machine. 11th Gen Intel Core i7-11370H @ 3.30 GHz, 4 cores / 8 threads (up to 4.8 GHz), 31 GiB RAM, Samsung SSD 990 PRO 2TB (NVMe) (ext4), Linux 7.0.0-38-generic x86_64, Ubuntu 26.04.1 LTS, glibc 2.43, gcc 15.2.0. Acer Nitro AN517-53. A development machine, with other work running at times; the A/B runs are alternated for that reason.

Build. RelWithDebInfo (-O2 -g -DNDEBUG), gcc 15.2.0, fully static: yes, TLS: OpenSSL 3.6.3 (bundled, static); mbedTLS not built on this machine. CONFIG_DEBUG_TRACK_MEMORY is on (the .config of this machine): every allocation is tracked. A build without it does less work per allocation; that build was not measured here.

The benchmarks are in performance/c/; the raw figures of this page are in 7.27.0.json; every A/B, change by change, is in performance/c/README.md and in the CHANGELOG.
