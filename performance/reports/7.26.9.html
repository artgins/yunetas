Yuneta 7.26.9: a hardening release that made the treedb faster

7.26.9 is a correctness release, out of sixteen rounds of review: the kw readers never hand back a freed default, a name that comes from data is a key and never a path, two name rules guard every treedb name, the logger honours the precision and the size of what it prints, and C_NODE refuses what a peer names with a warning after the permission. One of those changes pays: the treedb looks its topics, hooks and fkeys up by key instead of formatting and splitting a path, and a link or unlink is 12% faster, deleting a parent 8.7%, a reopen 6.2%, a forced delete 3.9%. Measured against 7.26.8 on the same machine, each release built from its own tree, the two run alternately. One price, said with its number: the event loop echo that appends every message to timeranger2 is 3.9% slower; the appends alone are 1.5% slower, at the edge of their noise. No code of that path changed, and the profiles of the two binaries show the same functions with the same weight: it is not traced to a change.

How it was measured

7.26.9 against 7.26.8. 7.26.8 and 7.26.9 each built from their own tree: a git worktree of the 7.26.8 tag with the same .config and compiler, where only the kernel libraries, the modules of modules/c, the benchmarks of performance/c/ and the three ctest binaries were built. outputs_ext was shared between the two trees: linux-ext-libs did not change in this release. Measured: the benchmarks of performance/c/ and the ctest binaries test_topic_pkey_integer, test_topic_pkey_integer_iterator2 and test_topic_pkey_integer_iterator5. The two binaries of each benchmark run alternately, the order flipped every round, with a sync and a 3 s pause before each run: 8 rounds; the three ctest binaries 24 rounds, 1 s pause. Mean +- standard deviation (median), t = the change over its standard error; |t| < 3 is noise, as in the reports before. The treedb figures are CPU time of the process per operation. No module was padded or relinked: a whole-release build also moves where the code lands, so a change of a few percent is not told apart from placement. Where a change was not traced to the code, the profiles of the two binaries (perf, test_topic_pkey_integer) were compared.

Absolute figures. The absolute figures of 7.26.9 are its side of the A/B run (the code of the release, built from the main tree): 8 rounds of the benchmarks of performance/c/, 24 of the three ctest binaries, a sync and a pause before each run, no CPU pinning. The per-second benchmarks drop their first and last second; reads page by page are the FORWARD pass. The binary sizes are those of the clean release build.

Machine. 11th Gen Intel Core i7-11370H @ 3.30 GHz, 4 cores / 8 threads (up to 4.8 GHz), 31 GiB RAM, Samsung SSD 990 PRO 2TB (NVMe) (ext4), Linux 7.0.0-38-generic x86_64, Ubuntu 26.04.1 LTS, glibc 2.43, gcc 15.2.0. Acer Nitro AN517-53. A development machine, with other work running at times; the A/B runs are alternated for that reason.

Build. RelWithDebInfo (-O2 -g -DNDEBUG), gcc 15.2.0, fully static: yes, TLS: OpenSSL 3.6.3 (bundled, static); mbedTLS not built on this machine. CONFIG_DEBUG_TRACK_MEMORY is on (the .config of this machine): every allocation is tracked. A build without it does less work per allocation; that build was not measured here.

The benchmarks are in performance/c/; the raw figures of this page are in 7.26.9.json; every A/B, change by change, is in performance/c/README.md and in the CHANGELOG.
