Yuneta 7.25.21: secrets masked everywhere, and nothing slower

7.25.21 is a security and correctness release. Credentials are masked in every trace, every kw the kernel dumps, the traffic dumps and view-config; a gbuffer can be marked secret (hidden from the dumps, wiped when it is freed); C_TCP and C_TCP_S stop and start again cleanly and count their connections; the rt_disk feeds of timeranger2 hear every delete. None of it is on the paths that run every second at the default trace levels: the masking runs only when a trace prints. Measured against 7.25.20 on the same machine, each release built from its own tree, the two run alternately: no figure is slower beyond the spread of its rounds, and no figure is claimed faster either.

Prices paid on purpose

What got slower, how much, and what it buys.

None. No figure of 7.25.21 is slower than 7.25.20 beyond the spread of its rounds. Three moved outside it, all of them faster, and none is claimed as a gain: the TCP echo through the gobj stack (+4.8% round trips), the BFF logins (+3.1%) and 600 000 appends to one key (-3.7% of time). No change of this release takes work off those paths (a TCP send gained a key lookup), the append code is the same as in 7.25.20, and the same append benchmark moved +3.6% the other way in the last report. Both releases are built whole, so the code lands at other addresses: that is placement, not speed.

How it was measured

7.25.21 against 7.25.20. 7.25.20 and 7.25.21 each built from their own tree: a git worktree of the 7.25.20 tag with the same .config and compiler, where only the kernel libraries, modules/c/test, the benchmarks of performance/c/ and the three ctest binaries were built. outputs_ext was shared between the two trees: linux-ext-libs moved from 1.22 to 1.23 in this release, but the change is only how openresty is downloaded, and no library changed version, so both sides link the same external libraries. Measured: the benchmarks of performance/c/ and the ctest binaries test_topic_pkey_integer, test_topic_pkey_integer_iterator2 and test_topic_pkey_integer_iterator5. The two binaries of each benchmark run alternately, the order flipped every round, with a sync and a 3 s pause before each run: 8 rounds, 24 for the three ctest binaries. Mean +- standard deviation (median). No module was padded or relinked: a whole-release build also moves where the code lands, so a change of a few percent is not told apart from placement.

Absolute figures. The benchmarks of performance/c/ on the build of 7.25.21, 5 rounds run after the A/B run, with a sync and a 3 s pause before each run, no CPU pinning. The appends and reads of the three ctest binaries are the 7.25.21 side of the A/B run (24 rounds). The per-second benchmarks drop their first and last second; reads page by page are the FORWARD pass.

Machine. 11th Gen Intel Core i7-11370H @ 3.30 GHz, 4 cores / 8 threads (up to 4.8 GHz), 31 GiB RAM, Samsung SSD 990 PRO 2TB (NVMe) (ext4), Linux 7.0.0-34-generic x86_64, Ubuntu 26.04.1 LTS, glibc 2.43, gcc 15.2.0. Acer Nitro AN517-53. A development machine, with other work running at times; the A/B runs are alternated for that reason.

Build. RelWithDebInfo (-O2 -g -DNDEBUG), gcc 15.2.0, fully static: yes, TLS: OpenSSL 3.6.3 (bundled, static); mbedTLS not built on this machine. CONFIG_DEBUG_TRACK_MEMORY is on (the .config of this machine): every allocation is tracked. A build without it does less work per allocation; that build was not measured here.
