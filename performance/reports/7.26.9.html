Yuneta 7.26.9: a hardening round that made the treedb faster

7.26.9 closes sixteen rounds of review: the kw readers never hand back a freed default, a name that comes from data is a key and never a path, two name rules guard every treedb name, the logger honours the precision and the size of what it prints, and C_NODE refuses what a peer names with a warning after the permission. This study compares it with 7.26.0, the last release with a study, so it covers 7.26.1 to 7.26.9, and places every move in its release and commit by building the tags and commits between them. It replaces the study made at the tag against 7.26.8, a release nobody had measured. The treedb is faster: a link or unlink 12% (8.59 -> 7.54 us of CPU), deleting a parent 10%, a reopen 9%, a forced delete 4%, from the names looked up by key. Two prices, each with its release: the first open of 40 treedbs takes 6.7% more (7.26.7: every treedb gets a topic __icons__ at its first open), and 600 000 appends to one key 4.1% more time (7.26.9: the kw calls of each append, hardened). The loss the first study could not trace (the event loop echo with an append, -3.9% against 7.26.8) is not there against 7.26.0.

How it was measured

7.26.9 against 7.26.0. Written on 2026-10-22, after the release, against 7.26.0: the last release with a study. It replaces the study made at the tag against 7.26.8, a release nobody had measured. It covers 7.26.1 to 7.26.9 (7.26.1 to 7.26.4 changed no code of the kernel libraries or the modules). 7.26.0 and 7.26.9 each built from a git worktree of its tag, with the same .config and compiler; in each tree only the kernel libraries, the modules, performance/c/ and the three ctest binaries were built, and the perf_timeranger2 of the main tree (with its read phase, public API only) was compiled into both. outputs_ext was shared: linux-ext-libs 1.24 (OpenSSL 3.6.5, PCRE2 10.49) on both sides, where both tags shipped with 1.23 (OpenSSL 3.6.3), so the A/B compares the code of the two releases. The two binaries of each benchmark run alternately, the order flipped every round, with a sync and a 3 s pause before each run (1 s for the three ctest binaries and the read phase): 15 rounds (the first left out: it ran right after a build on the machine); 31 for perf_timeranger2 (47 for its appends, opens and tm query), perf_tr_treedb and perf_c_treedb, with the tags between them in some rounds (7.26.6, 7.26.7 and 7.26.8); 24 for the read phase alone (a first run of 24 was left out: a build of another tree ran during it). To place each move, the figures that moved were measured again on the tags between and on commits of 7.26.9, 16 rounds each, every build in one rotation. Mean +- standard deviation (median), t = the change over its standard error; |t| < 3 is noise. The treedb figures are CPU time of the process per operation.

Absolute figures. The absolute figures of 7.26.9 are its side of this A/B run: the code of the tag, built on 2026-10-22 from a worktree of the tag, on the machine of the earlier reports, with the external libraries of 1.24. The per-second benchmarks drop their first and last second; reads page by page are the FORWARD pass. The binary sizes are those of the release build of 7.26.9, kept from the first report.

Machine. 11th Gen Intel Core i7-11370H @ 3.30 GHz, 4 cores / 8 threads (up to 4.8 GHz), 31 GiB RAM, Samsung SSD 990 PRO 2TB (NVMe) (ext4), Linux 7.0.0-38-generic x86_64, Ubuntu 26.04.1 LTS, glibc 2.43, gcc 15.2.0. Acer Nitro AN517-53. A development machine, with other work running at times; the A/B runs are alternated for that reason.

Build. RelWithDebInfo (-O2 -g -DNDEBUG), gcc 15.2.0, fully static: yes, TLS: OpenSSL 3.6.5 (bundled, static: linux-ext-libs 1.24 on both sides; both tags shipped with 1.23, OpenSSL 3.6.3); mbedTLS not built on this machine. CONFIG_DEBUG_TRACK_MEMORY is on (the .config of this machine): every allocation is tracked. A build without it does less work per allocation; that build was not measured here.

The benchmarks are in performance/c/; the raw figures of this page are in 7.26.9.json; every A/B, change by change, is in performance/c/README.md and in the CHANGELOG.
