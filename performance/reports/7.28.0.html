Yuneta 7.28.0: twice the records, half the cost of an event

7.28.0 is a performance round over the whole C SDK, and Yuneta's own JSON library: jansson from github.com/artgins/jansson, upstream v2.15.1 with a series of Yuneta's commits. A yuno of 7.28.0 stores 1.9 times the records per second, reads 2.5 times as many, opens a treedb 17 times faster, and sends an event to another yuno and gets its answer twice as fast. The API is the same. Against 7.27.11, the last release with a study: 40 of 50 figures faster outside their noise, none slower.

Where the gain comes from

A third build ran in the same rotation: the C code of 7.28.0 with the jansson of 7.27.11. Its bar is between the two releases: what is left of the gain is jansson's. timeranger2 owes most of its gain to jansson, because a record is a json that is dumped when it is written and parsed when it is read. The treedb and the network owe most of theirs to the rest of the round: the subscriptions read from a C record, no EV_STATE_CHANGED that nobody sees, the treedb open of the newest record of a key, the indexed hooks, a websocket frame in one write. The three builds ran 8 rounds (12 for the appends and the reads), so their figures differ a little from the A/B above. The rest of the round includes jansson's allocators without zeroing (gbmem_get_json_allocators()), and 7.27.12 to 7.27.21 (only c_authz.c changed in the kernel).

Prices paid on purpose

What got slower, how much, in which release, and what it buys.

None. Two figures of the rotatory measured slower in the rotation of the study, the log record +1.0% (t = 3.4) and the audit record with its retention +1.8% (t = 8.0). The rotatory is the same code in both releases. In a controlled rotation, the same 7.28.0 moved by 64, 128 and 192 bytes measured the log record from +0.3% to +1.45% and the audit record with retention from +0.06% to +2.2% against 7.27.11: code placement, not code. The event loop alone (perf_yev_ping_pong, no gobj, no json) stays where it was, +0.5% (t = 1.2): the gain is in the layers above it.

How it was measured

7.28.0 against 7.27.11. Written on 2026-10-25, before the tag. 7.28.0 is the C code of main at d7c3e63e9 (the commits after it change no C of a library). It is measured against 7.27.11, the last release with a study; the releases between them (7.27.12 to 7.27.21, lite releases of the agent and the controlcenter) changed only c_authz.c in the kernel and are inside the same comparison. No figure got slower, so no tag between them had to be measured on its own. Each release built from a git worktree with the same .config and compiler, each with its OWN outputs_ext: 7.27.11 with the jansson of linux-ext-libs 1.25 (upstream v2.15.1 + patches/jansson/0001, atomic reference counts), 7.28.0 with linux-ext-libs 1.26 (jansson 2.15.1-yuneta.1, JANSSON_THREAD_SAFE_REFCOUNT=OFF); the other libraries are the same build. In each tree the kernel libraries, the modules, performance/c/ and the three ctest binaries were built; each tree runs its own benchmark sources, which differ only in the allocators given to jansson (7.28.0's take gbmem_get_json_allocators(), as every yuno of 7.28.0 does). The three benchmarks new in 7.28.0 (perf_ievent, perf_mqtt, perf_tr_treedb_read) were built in the 7.27.11 tree too, with the allocators of 7.27.11. The two binaries of each benchmark run in rotation, the order turned every round, with a sync and a 3 s pause before each run (1 s for the three ctest binaries and the read phase): 8 rounds; 24 for perf_tr_treedb, perf_timeranger2, the echoes, the BFF logins, perf_ievent and perf_mqtt; 48 for the append test (the test_topic_pkey_integer chain) and for the read phase; perf_rotatory and perf_tr_treedb_read 16. The two rotatory figures that measured slower were re-run in a controlled rotation of five binaries: 7.27.11, 7.28.0, and 7.28.0 relinked with 64, 128 and 192 bytes of pad before the libraries (the same machine code, moved). A third build, the code of 7.28.0 with the jansson of 7.27.11, ran in a three-way rotation (8 rounds, 12 for the appends and the reads) to split each gain between jansson and the rest. Mean +- standard deviation (median), t = the change over its standard error; |t| < 3 is noise. The treedb figures are CPU time of the process per operation.

Absolute figures. The absolute figures of 7.28.0 are its side of the A/B run: its C code (d7c3e63e9), built on 2026-10-25 on the machine of the earlier reports. The per-second benchmarks drop their first and last second; reads page by page are the FORWARD pass. The binary sizes are those of the yunos built from the main tree at the same C code, with the same .config.

Machine. 11th Gen Intel Core i7-11370H @ 3.30 GHz, 4 cores / 8 threads (up to 4.8 GHz), 31 GiB RAM, Samsung SSD 990 PRO 2TB (NVMe) (ext4), Linux 7.0.0-38-generic x86_64, Ubuntu 26.04.1 LTS, glibc 2.43, gcc 15.2.0. Acer Nitro AN517-53. A development machine, with other work running at times; the A/B runs are alternated for that reason.

Build. RelWithDebInfo (-O2 -g -DNDEBUG), gcc 15.2.0, fully static: yes, TLS: OpenSSL 3.6.5 (bundled, static: linux-ext-libs 1.26 in 7.28.0, 1.25 in 7.27.11); mbedTLS not built on this machine. CONFIG_DEBUG_TRACK_MEMORY is on (the .config of this machine): every allocation is tracked. A build without it does less work per allocation; that build was not measured here.

The benchmarks are in performance/c/; the raw figures of this page are in 7.28.0.json; every A/B, change by change, is in performance/c/README.md and in the CHANGELOG.
